# 研脉 · PaperPulse：定位与开发顺序

更新：2026-10-06。当前已完成论文导入、原文阅读和正文材料持久化；AI 解读链路已接入，模型调用按配置启用。另已接入 arXiv 自动发现、每日候选队列、方向趋势、本地每周阅读信号，以及按 OpenAlex 引用数据和 CCF A venue 名单筛选的高引参考，仍需真实来源和浏览器验收。

## 产品主线

**围绕论文热点追踪，把论文内容、原文证据、AI 解读和代码链接放在一起。** 首页借用 AIHOT 的信息流壳层承载论文脉搏，新闻与热点导航保留为底座能力。这是一个范围有限的论文解读应用，不扩展为通用研究 Agent 或完整文献管理平台。

先让用户把一篇真实论文放进来，系统解析正文并生成一份带证据回跳的阅读卡片，再解决如何组织多篇论文。手写笔记不作为首轮主流程。

## 已有事实

- 独立项目采用 AIHOT 的 TypeScript / React Router SSR / Fastify / PostgreSQL 底座，新增业务在 `modules/papers/`。
- 已有论文库、手动添加、PDF.js 原文阅读、代码链接和阅读状态。旧笔记表和接口保留兼容性，但详情页首轮只展示 AI 解读、原文和代码资源。PDF 最多 20 MB，暂存数据库 bytea。
- arXiv 链接已经可以预览元数据，并在确认导入时尽量保存本地 PDF；本地 PDF 也可以单独导入，没有来源链接时使用内部论文身份。正文材料的正式解析器已接入 MinerU API：Node 端负责上传、轮询和下载结果，`content_list.json` 与 `full.md` 在入库前归一化为带页码、块类型和来源定位的材料块。未配置 token 时，arXiv 才会使用明确标注的 HTML 轻量回退；这不是 AI 导读。arXiv 自动发现和每日阅读队列已接入，部署安全开关默认关闭；OpenAlex/CCF A 高引参考已接入，真实来源抽检仍待完成。PDF.js 渲染不能当作全文入库。
- 当前仅单人本地使用；论文、材料和解读接口受管理员身份保护。模型调用通过上游 `chatJson` 统一记录模型、提示版本和 receipt；未配置时明确显示“等待模型配置”。
- 上游新闻代码还在，但论文主界面不展示；不能把上游全部功能算作本项目新增贡献。

## 按顺序交付

每阶段完成验收后再进入下一阶段，不并行铺开页面和功能。

| 阶段 | 只解决的问题 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1：减少导入和阅读摩擦 | 用户不应手填一整份论文档案 | 粘贴 arXiv 链接并预览元数据，确认时尽量保存本地 PDF；本地 PDF 可直接导入；按需生成正文材料 | 一篇真实论文能自动预览、导入、打开本地原文并生成正文材料 |
| 2：生成一份有出处的论文阅读卡片 | 快速了解论文具体做了什么 | 结构化 AI 解读固定包含一句话结论、研究问题、核心方法、实验设置与结果、局限；每个可验证主张绑定证据块 ID | 用真实论文核对内容，实验部分覆盖正文相应章节；证据按钮能回到原文；材料或模型不可用时明确说明 |
| 3：把论文组织成研究热点 | 首页帮助回顾一个方向的论文脉搏 | arXiv 热点/个人关注计划、候选列表、每日配额和方向趋势 | 自动检索可按部署开关运行；计划命中、推荐理由与趋势窗口可在页面追溯 |

阶段 1、2、3 的首批实现已经落地。下一步以真实部署和浏览器验收为主，确认 arXiv 发现质量、任务恢复、解读证据和阅读信号；期刊/会议及引用量来源等扩展在稳定使用后另行设计。

首轮界面只保留三个页面：论文首页、导入页、论文详情。首页以论文脉搏、搜索和主题标签为主；详情只保留 AI 解读、原文、代码与资源三个标签。证据回跳保留，因为它直接服务阅读核对。

## 复用旧项目的边界

2026-10-06 已核对 Research Pulse 源码，以下能力确实存在；本次仅检查代码，没有重新验证远程解析服务可用性。

| 旧能力 | 代码位置 | 新项目如何使用 |
| --- | --- | --- |
| PDF 接收、校验、内容哈希 | `research_pulse/workbench/paper_ingest.py` | 复用校验与内容去重规则；适配新项目存储，不迁入旧文件缓存和工作台数据库 |
| arXiv 链接识别、PDF 下载 | `research_pulse/workbench/paper_download.py` | 复用链接规范化、下载边界及测试用例；第一阶段仅承诺 arXiv 链接入口 |
| MinerU 上传、轮询、结果转换 | `research_pulse/production/mineru_api.py` | 已在 `modules/papers/backend/mineru.ts` 以 Node 适配器接入；沿用上传、轮询、ZIP 结果和 content_list 归一化边界 |
| 结构化正文及原文定位 | `research_pulse/production/normalized.py` | 保留新流程实际用到的正文块、页码、来源、文件哈希及完整结果校验；不迁入无关合并策略 |
| arXiv HTML 转换 | `research_pulse/production/html_adapter.py` | 仅作为未配置 MinerU token 时的开发回退；材料中的 parser 会明确写成 `arxiv-html-lite` |

旧项目运行时已将 MinerU 适配器接入论文准备队列。它返回全文 Markdown、结构化块和相关资源，不等于自动获得完整可靠的标题、作者、日期；元数据需单独处理，缺失值不生成假数据。

Node 主应用、PostgreSQL 和现有登录机制保持一致。若旧 Python 解析适配器可以独立运行，阶段 1 优先用范围有限的 Python 命令处理单篇 PDF，通过明确的输入/输出交给 Node；不启动旧 FastAPI、SQLite 工作台、ResearchSession、Harness 或 Agent。接入前验证独立调用、结果文件完整性和进程错误处理。Python 只负责解析，不形成第二套业务后端；必要的后台任务优先使用底座现有能力。

## 明确后置

期刊/会议与高引用量多源聚合、聊天和深度研究、多智能体、自动代码复现、知识图谱、向量知识库、多用户协作暂不进入首批实现。公开部署单独验收真实身份、私有数据访问与密钥配置，完成前不宣称上线。

下一步不改技术栈、不重写旧解析器、不增加大型平台页面。先完成真实使用验收，再按证据决定数据源扩展。

实际交付和测试边界见 [第一条阅读闭环](first-reading-loop-2026-10-06.md)。
